# Set up local development

The repository contains the Rust API, the GPUI desktop client, and a PostgreSQL Compose service. The API stores installation state in PostgreSQL, serves authenticated loopback HTTP, and runs the provider CLIs (Codex, Claude Code) on the host, each turn in the bot's project directory. The desktop connects to it as the owner.

## Prerequisites

For an installation rather than a development checkout, use the installer (see [Install](../README.md#install)); it keeps everything in `~/.else` and is tested by `scripts/test-install.sh` in Debian, Ubuntu, and Arch containers. A development checkout uses the root `.env` and `~/.local/share/else-bot` as below.

Install Rust with Cargo and rustfmt, Docker Engine with Docker Compose, and the PostgreSQL 18 client tools (`pg_dump`, `pg_restore`; checked with 18.6) for backups. Checked with Rust 1.98.0 and Compose 5.6.1. The desktop also needs the Linux libraries listed under [Run the desktop](#run-the-desktop). Run the commands below from the repository root.

To chat through Claude as well, install Claude Code (verified with 2.1.316), log in once by running `claude` as the API user, and save an explicit Claude profile (see [Claude provider](#claude-provider)).

To chat through Codex, install the Codex CLI (verified with 0.166) and log in once with `codex login` as the user that runs the API. A version-manager shim such as mise's is resolved to the real binary; otherwise set `ELSE_CODEX_BIN` to the native `codex` executable. Without Codex the API still runs, and the capabilities report why Codex is unavailable.

The saved Codex profile is GPT 6.1 Sol Medium Fast (`gpt-6.1-sol`, `medium`, `priority`), seeded by `else-api setup` and editable through the [saved profile contract](providers.md#saved-execution-profile). Provider-native sub-agents are always disabled.

### macOS

A development checkout builds and runs on macOS (checked on macOS 26.6, Apple silicon, Rust 1.99.1, OrbStack 29.8 for Docker). The desktop, the API, the database, memory, backups and restore, Codex, the synthetic provider, and bot computers work.

Bot computers need Microsandbox 0.7.13 (its installer puts `msb` in `~/.microsandbox/bin` with `lib/libkrunfw.*.dylib`; Apple silicon uses the Hypervisor framework, no `/dev/kvm`). Build and load the guest image into the checkout's runtime home with `scripts/build-guest-image.sh` (about 15 minutes the first time), then set `ELSE_VM_IMAGE=else-guest:2` and `ELSE_VM_DESKTOP=1` in `.env`, as an installation does. Without Microsandbox, bot computers report unavailable, as on Linux.

```sh
brew install postgresql@18 && brew link --force postgresql@18   # pg_dump, pg_restore on PATH
```

Use any Docker with Compose (Docker Desktop or OrbStack) for `docker compose up -d --wait`. The backup tools are looked up on the API's `PATH`, or set `ELSE_PG_DUMP` and `ELSE_PG_RESTORE` to absolute paths. The desktop builds with the Command Line Tools; Xcode is not required. Use `ELSE_SYNTHETIC_PROVIDER=1` to chat without a host provider.

Codex needs the verified version (0.166; `brew upgrade --cask codex`) and `codex login`. Claude Code needs the verified version (2.1.316; `claude install 2.1.316`) and a login, as in a terminal: bots use the host's Claude configuration, so the Keychain login works. Leftover provider processes from a crashed API are swept at startup on macOS too (through libproc; see [security](security.md#host-provider-processes)).

## Configure the development services

Create the local environment file if it does not exist:

```sh
test -e .env || cp .env.example .env
```

Edit `.env` for your local setup. Git ignores this file. Its example credentials are for the local development database.

| Variable | Default | Purpose |
| --- | --- | --- |
| `COMPOSE_PROJECT_NAME` | `else-dev` | Namespaces containers, the network, and the data volume. Use a different value for another checkout. |
| `COMPOSE_FILE` | `infra/compose.yaml` | Lets root-level Compose commands find the infrastructure definition. |
| `POSTGRES_DB` | `else` | Database created on first initialization. |
| `POSTGRES_USER` | `else` | Development database user created on first initialization. |
| `POSTGRES_PASSWORD` | `else_dev_only` | Local development password. |
| `POSTGRES_PORT` | `5432` | Host port bound to `127.0.0.1`. Change it if another database uses that port. |

Compose reads these settings from the root `.env`. The file selection and project name use [Compose's predefined variables](https://docs.docker.com/compose/how-tos/environment-variables/envvars/). Only the three PostgreSQL initialization variables are passed into the container. Adding future API secrets to `.env` does not automatically expose them to PostgreSQL.

## Start PostgreSQL

Validate the configuration, then start the database and wait for its health check:

```sh
docker compose config --quiet
docker compose up -d --wait
docker compose ps
```

The service uses `postgres:18.6`, password authentication for TCP connections, and a persistent named volume. Its health check uses TCP so the temporary initialization server does not report ready. PostgreSQL 18 stores its versioned data directory under `/var/lib/postgresql`, which is the volume mount used here. See the [official image documentation](https://hub.docker.com/_/postgres).

Compose also starts `seaweedfs` (`chrislusf/seaweedfs:4.50`, `server -dir=/data -s3 -s3.port=8333`, a named volume, bound to `127.0.0.1:8333`): a local S3 emulator for the backup replication tests, with synthetic keys from the `ELSE_TEST_S3_*` entries in `.env` (copy them from `.env.example`). It never stands in for a real bucket in normal use.

Open a database shell inside the container:

```sh
docker compose exec postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
```

For a client running on the host, use `127.0.0.1`, the configured port, database, user, and password. The default connection URI is `postgresql://else:else_dev_only@127.0.0.1:5432/else`. Percent-encode credentials if you construct a URI with different values. The API reads `DATABASE_URL`, or builds this URI from the `POSTGRES_*` variables when `DATABASE_URL` is unset.

## Run the API

Start PostgreSQL, provision the installation once, then start the API from the repository root:

```sh
docker compose up -d --wait
cargo run -p else-api -- setup
cargo run -p else-api -- serve
curl -s http://127.0.0.1:7879/healthz
printf 'Authorization: Bearer %s\n' "$(cat ~/.local/share/else-bot/owner-token)" |
	curl -s -H @- http://127.0.0.1:7879/v1/capabilities
```

`serve` is the default command. The process reads the root `.env` when present, and variables already set in the environment take precedence. A `.env` that exists but cannot be parsed fails startup without printing its contents. Configuration is validated before the API opens any file or listener. An invalid value exits with status 1 and names the variable without echoing secret values. Ctrl-C or `SIGTERM` stops accepting connections, drains requests, and closes any remaining connections after the grace period.

`setup` is the explicit installation step. It creates the data directory with mode `0700` and each missing credential file with mode `0600`, applies migrations, seeds any missing provider profile, and creates the main bot `Assistant` with its conversation the first time. Running it again reports `kept existing` and changes nothing: saved profiles keep their values, and a deleted main bot or cleared default stays as it is. It never replaces an existing or malformed file and prints paths, never values. `serve` never creates credentials. It exits with an error naming `else-api setup` when a file is missing, and rejects malformed or empty values, symbolic links, files owned by another user, files readable by group or others, and credential directories writable by others. The file is opened without following symlinks and validated through the opened descriptor.

### Owner routes

The implemented routes follow the [desktop contract](research/desktop-and-feature-contracts.md#proposed-rest-endpoints):

| Route | Behavior |
| --- | --- |
| `GET /v1/capabilities` | API version, per-process `server_instance_id`, enabled providers with availability (`available`: a message can be sent now; `cli_available`: the CLI runs here) and each provider's `catalog` (the exact models, reasoning efforts, and service tiers it applies; `priority` is Fast), the `defaults` new bots start with, and limits. Credentials are not exposed. |
| `GET /v1/bots[?include_deleting=true]` | `default_bot_id` and active bots, oldest first. `include_deleting` adds tombstones whose shutdown is pending. |
| `POST /v1/bots` | `{request_id, name, role, profile?}`; `profile` is `{provider_id, model, reasoning_effort, service_tier}`, checked by that provider's adapter before anything is created. `201` with `Location` on first acceptance; the same request returns `200` with the same bot; changed input under that ID returns `409 request_conflict`. |
| `GET /v1/bots/{id}` | An active bot, or a deletion receipt with `cleanup.state` and no role or conversation reference. |
| `DELETE /v1/bots/{id}` | Refuses the main bot (`409 main_bot`: it is never deleted). Otherwise commits the tombstone, ends queued messages, and interrupts running work before returning. `200` with `cleanup.state = done` when nothing was running; `202` with `pending` while the provider stops, after which the bot becomes `deleted`. Repeating it returns the same receipt. History and conversations are retained, and late provider output is never appended. |
| `GET`, `PUT /v1/bots/{id}/profile` | The bot's own provider and model (`own: true`), else the defaults it uses (`own: false`). `PUT` takes a complete `{provider_id, model, reasoning_effort, service_tier}` and applies from the bot's next message. |
| `POST /v1/onboarding` | The welcome screen: `{name, profile}` renames the main bot, gives it that provider and model, makes them the defaults, and records completion (`onboarding_required` in the capabilities turns false). Existing installations show it once too. |
| `GET`, `PUT /v1/settings/defaults` | The provider and profile bots without their own use (and new bots start with): the chosen default provider, else the first available one that takes a profile, with that provider's saved profile. `PUT` sets both. |
| `POST /v1/bots/{id}/cancel` | Stop work: `{request_id}`. Ends every queued message and interrupts the running one accepted up to now. `202 {state: "pending"}` until the provider has stopped, then `200 {state: "done"}`. New messages get `409 cancellation_pending` meanwhile. Retrying a completed request ID returns its receipt and never affects later messages. |

| `POST /v1/bots/{id}/turns` | `{request_id, text, provider_id?}`; without `provider_id` the bot's own provider, else the default. The turn snapshots the bot's own profile when it is for that provider, else the provider's saved one. Saves the owner message and a queued turn in one transaction, then wakes the scheduler. `202` on acceptance; a matching retry returns `200` with the same item and turn; different text or provider under that ID returns `409`. A deleted bot returns `410 bot_deleted`. More than four waiting messages return `429 queue_full` with `Retry-After`. A `null` provider uses the default. |
| `GET /v1/bots/{id}/turns/by-request/{request_id}` | Resolves a lost send response, or `404`. |
| `GET /v1/bots/{id}/conversation[?limit=50&before_seq=N]` | Consistent snapshot read in one repeatable-read transaction: the newest `limit` items (1 to 200) in ascending `seq`, their turns plus every unfinished turn, activity, `older_before_seq` for the previous page (or `null`), and `event_cursor`. |
| `GET /v1/ws` | Owner WebSocket for live updates. Subscribe to `bots` (pushed list) and `bot:<id>` (committed events after a snapshot cursor). Event kinds are `item.upsert`, `item.delta`, `turn.updated`, and `bot.updated`. See [events and reconnecting](#events-and-reconnecting). |
| `GET`, `PATCH /v1/settings/providers/{provider_id}` | Read or update the saved execution profile. `PATCH` takes any of `model`, `reasoning_effort`, `service_tier`, and an optional `expected_revision`. The adapter validates the exact values; unsupported values return `400 invalid_profile` and nothing changes. A change bumps the revision. Accepted turns keep the revision they were accepted with. |

Unknown or malformed IDs return `404 not_found`, always after authentication. A role over 8 KiB or message text over 32 KiB returns `413 too_large`; other invalid input, including NUL characters, returns `400 invalid_input`. Try it with a synthetic bot:

```sh
printf 'Authorization: Bearer %s\n' "$(cat ~/.local/share/else-bot/owner-token)" |
	curl -s -H @- -H 'Content-Type: application/json' \
	-d "{\"request_id\":\"$(uuidgen)\",\"name\":\"Work\",\"role\":\"Help with my work\"}" \
	http://127.0.0.1:7879/v1/bots
```

### Sidebar categories

Bots can be grouped into flat, owner-managed categories (POC-030; `bot_categories`, `category_requests`, and `bots.category_id`, migrations `0027` and `0028`). Existing bots start unassigned. The routes are `GET/POST /v1/categories`, `PATCH/DELETE /v1/categories/{id}`, and `PATCH /v1/bots/{id}/category` (see the [desktop contract](research/desktop-and-feature-contracts.md)). Names are trimmed, 1 to 80 characters, without control characters, and unique by a Unicode case-folded key the API computes (`name_key`; uppercasing then lowercasing, so Straße and STRASSE collide); categories are listed by that key's bytes (code point order) with the ID as tie-breaker, the same on any database collation. Creation is idempotent per request ID like bot creation, and request IDs are one namespace: a category's request ID cannot create a bot or stop work, and theirs cannot create a category. Lock order is a category row before a bot row, and category operations never hold more than one bot row: deletion marks the category `deleting` (it disappears from every list and takes no new assignment), unassigns its bots one per transaction (each journals `bot.updated`), then removes the row, so it cannot deadlock with bot deletion or Stop work, which lock several bots; an interrupted deletion is finished by the next `DELETE`, and clients meanwhile see the category gone and its remaining bots in the unassigned group. Assignment locks the category (refusing one being deleted) and then the bot, which must be active, so a deleted bot is never revived. A category changes nothing but the sidebar grouping. `GET /v1/bots` and the `bots` WebSocket snapshot carry `categories[]` from the same read-only snapshot as the bots, and each bot's `category_id`; changes to a category's own row wake the `bots` channel with a notification for no bot, so every client sees renaming, creating, or deleting an empty category. Task grants never reach these routes. Backups include the tables like any other.

### Turns and the scheduler

One scheduler runs inside the API. PostgreSQL rows are the queue: it claims the oldest queued message of each idle bot, oldest first across bots, within `ELSE_MAX_ACTIVE_TURNS`. A unique index allows one active turn per bot. Turn status moves through `queued`, `preparing`, `sending`, `running`, and a terminal `completed`, `interrupted`, `failed`, or `uncertain`. Assistant text is persisted at most every 100 ms or 2 KiB under one stable item ID. The completion of a turn comes only from the adapter's terminal outcome, never from text.

History `seq` is arrival order. A message queued behind a running turn can therefore precede that turn's reply; each item carries its `turn_id`.

On startup the API takes two singleton locks before reading or changing runtime state: an exclusive lock on `$ELSE_DATA_DIR/api.lock` and a PostgreSQL session advisory lock. A second API on the same data directory exits with `another else.bot API is already running`, and one on the same database with `another else.bot API is already using this database`, before reconciling or dispatching anything. It then binds the listener and reconciles: a turn claimed but never sent returns to the queue; a turn that may have reached its provider, including one being stopped, becomes `uncertain` with `effect_uncertain = true` and is never resent; pending stops and deletions waiting on those turns complete.

An interrupted provider has 10 seconds to stop. If it does not, its turn is recorded as `uncertain` rather than claiming the action was undone.

### Codex provider

The `codex` provider is listed first and is the default when available. It reports unavailable, with the reason, when the CLI or the host login is missing. Each turn starts `codex app-server` on the host in the bot's project directory (`CODEX_HOME` is the bot's own `$ELSE_DATA_DIR/bots/<bot>/codex-home`, with the host `auth.json` linked into it), opens or resumes the bot's native thread, sends the message with the saved profile (`gpt-6.1-sol`, `medium`, `priority` by default) on thread start or resume and on turn start, streams the reply, and stops the process after the terminal event. The settings Codex reports back must equal the requested ones or the turn fails with `profile_mismatch`. A native thread is reused while its fingerprint (prompt version, project directory, tool and agent policy, profile, bot name and role) matches. A changed profile or role, or a thread Codex can no longer resume, starts a new thread and sends earlier history from PostgreSQL (whole messages, newest first, within 32 KiB) ahead of the owner's message. History handled by another provider since the thread last ran is sent the same way. Stop work sends `turn/interrupt` and keeps the partial reply. A turn's tools are Codex's own shell and file tools, with full host access and never asking for approval (`sandbox_mode = "danger-full-access"`, `approval_policy = "never"`, `shell_tool` on), and else.bot's tools: the per-launch configuration names one MCP server, `elsebot`, at the API's `/tools/v1/mcp`, with only else.bot's tools enabled. The turn's task grant reaches Codex through the `ELSE_TASK_GRANT` environment variable and is never written to disk. For this model Codex calls MCP tools from its code-mode host (`codex-code-mode-host`, beside the CLI). Preflight requires exactly that server and those tools. A web, image, dynamic-tool, or native-agent item, an MCP call outside the allowlist, or any approval request ends the turn as `policy_violation`; commands and file changes are allowed. Memory summaries run with no tools and a read-only sandbox. Reasoning text is never stored.

Profile updates accept models `gpt-6.1-sol`, efforts `low` to `max`, and tiers `default` or `priority`. `ultra` is refused because it delegates to native sub-agents. Only Codex versions whose policy controls were verified (0.166) are offered; another version reports unavailable unless `ELSE_CODEX_ALLOW_UNVERIFIED=1` is set after checking it. The fingerprint also covers the CLI version and the logged-in account, so changing either starts a new native thread. A session that may hold an uncertain delivery is never resumed. Events are matched to the current thread and turn, and a model reroute or settings change away from the saved profile ends the turn as `profile_mismatch`.

Live checks use the owner's subscription and run only on request:

```sh
ELSE_LIVE_CODEX=1 cargo test -p else-api --test codex_live -- --nocapture
```

### Claude provider

The `claude` provider (POC-020) runs Claude Code (verified with 2.1.316; `ELSE_CLAUDE_BIN`, else `claude` on `PATH`, with a mise shim resolved to the real binary) on the host in the bot's project directory with the host's own Claude configuration, as `claude` runs in a terminal: `$CLAUDE_CONFIG_DIR` when the API was started with it (passed on), else the CLI's default `~/.claude`, left implicit because on macOS the Keychain entry holding the login depends on it. The login is wherever Claude Code keeps it (`.credentials.json` on Linux, the Keychain on macOS); the provider checks it at startup with `claude auth status`. Native sessions are stored there under `projects/<bot's resolved project path, non-alphanumerics as ->`, so a bot only ever resumes its own; else.bot's locked settings and MCP configuration are private files in `$ELSE_DATA_DIR/bots/<bot>/claude-home`, passed by path (`--settings`, `--mcp-config`), and `--setting-sources ""` keeps the owner's own settings, hooks, plugins, and `CLAUDE.md` files out. Log in once by running `claude` as the API user. No profile is seeded: Claude is reported unavailable in the capabilities until an explicit profile is saved with `PATCH /v1/settings/providers/claude {model, reasoning_effort, service_tier}` (a first profile needs all three fields; models `claude-opus-5-5`, `claude-sonnet-5-5`, `claude-haiku-5-5`, `claude-fable-5-1`, efforts `low` to `max`, tier `default`; an alias such as `opus` is refused because it follows the CLI's floating default). Messages for a provider without a saved profile are refused.

Each turn starts one `claude -p` process with stream-json input and output, user-message replay, and partial messages, the saved model and effort, an else.bot system prompt (`--system-prompt`, prompt `else-claude-v6`), `--tools` limited to the host shell and file tools (`Bash`, `Read`, `Write`, `Edit`, `NotebookEdit`, `Glob`, `Grep`; no web, skills, or `Agent` sub-agents, which are denied again in the settings file `else-settings.json`, with hooks and auto-memory off), `--setting-sources ""`, `--strict-mcp-config` with else.bot's MCP server only (`elsebot-mcp.json`, whose bearer header references `ELSE_TASK_GRANT` from the environment), the host tools and else.bot's pre-approved by name, `--permission-mode dontAsk`, and `--disable-slash-commands`. Both files are rewritten before every launch. A new session gets a UUID chosen by the API (`--session-id`); the next turn resumes it with `--resume <id>` only if its fingerprint matches and its transcript is in this bot's home, otherwise a new session is started and the conversation rebuilt from PostgreSQL. The `system/init` event must report exactly the host tools and else.bot's, else.bot's server connected, and the saved model; any other tool use, a permission request (answered with a denial), a task lifecycle event, an event carrying a parent tool use (a sub-agent), or a different model in a message ends the turn as `policy_violation` or `profile_mismatch`. The built-in agent names Claude lists in `init` are not taken as proof of anything; without the `Agent` tool they cannot run. The owner's message carries an API-chosen UUID and is accepted only when its replayed echo arrives. A `result` before that echo is a refusal (`provider_refused`) only when it is an error with no model turn and no output at all; anything else is `uncertain`. Completion comes only from the terminal `result`, and only after a verified `init`. Writes to the CLI are bounded (30 seconds), and event lines are read without losing a partly read line when a timer or a stop wins. A process killed without a result (including a parked delegating attempt) has its native session retired. Stop work sends the CLI's `interrupt` control request; without a result within 15 seconds the process group is terminated and the turn is `uncertain` (its session is then retired).

### Provider switching

Each owner message is bound to the provider it was sent with. A message for another provider moves the bot's active turn on the other provider to `cancelling` in the same transaction and interrupts it, so the switch does not wait behind it (its output is recorded as it drains; guest jobs keep running). and each provider keeps its own native session per conversation with `considered_through_turn`, the last owner turn whose settled history it has seen. A session is sent only what it missed, so a session returning after another provider gets just the other provider's turns. When a turn's provider differs from the previous owner turn's and the receiving session missed something, the API freezes history at the previous turn and records a handoff (`handoffs`, migration `0017`) before anything is sent. It asks the outgoing provider for a checkpoint of at most 8 KiB within 60 seconds (prompt `else-handoff-v1`, never including the owner's new message), run with no tools at all and verified so: Codex in an ephemeral no-MCP thread under `codex-summary`, Claude with no tools, no MCP server, and no session persistence under `claude-summary`, its `init` confirming both. When the outgoing provider is not configured, unavailable, fails, times out, cannot prove a no-tool run, or returns too much, the handoff is `fallback` with the reason and the receiving session gets the recorded history alone. The receiving packet is the handoff note and checkpoint (marked historical), the missed history (whole items within 32 KiB, the first owner message first, then the newest; omitted turns are listed by number; the request and reply of a turn that did not complete are both marked with its status, such as `interrupted` or `uncertain`), the API's own records of the bot's running and recently lost guest jobs (ID, status, start time, command) regardless of which history was selected, and the owner's message exactly once. The checkpoint request carries the same job records. The handoff records the selected and omitted turns, a SHA-256 of the packet, and the receiving session, and follows delivery: `prepared`, `sending` when the turn starts sending, `accepted` on the provider's correlated acknowledgment, `uncertain` when delivery is unknown (including after a restart or an orphaned turn), or back to `prepared` on an explicit refusal. A session that may hold an uncertain delivery is never resumed. Guest jobs, artifacts, and memory belong to the bot, not to a provider: the receiving provider finds a running job by its ID and checks it with `computer_job`.

### Memory

Each bot has an immutable, ordered memory log (`memory_entry`, zero-based `seq` per bot). Owner messages enter it when accepted; assistant replies enter it with their final text when the turn ends, including partial replies of stopped, failed, or uncertain turns. Both are written in the same transaction as the conversation change, keyed `item:<id>`, so a retried send adds nothing. Texts over 64,000 bytes are split at UTF-8 boundaries into ordered parts. Migration `0006` backfilled existing history the same way. Entries cannot be updated or deleted. Search uses PostgreSQL's `simple` text configuration (lexical, not semantic).

Authority follows the kind: `owner` only for owner messages and explicit corrections, `assistant` for replies, `tool` for tool activity. A correction exists only through the owner route below and must supersede an earlier owner entry of the same bot; a database check and trigger enforce this as well. Search hides superseded entries unless asked, and reads show `supersedes_seq` and `superseded_by`.

| Route | Behavior |
| --- | --- |
| `GET /v1/bots/{id}/memory[?start_seq&count]` | The original entries with source, authority, parts, and correction links, plus `length`. `410` for a deleted bot. |
| `POST /v1/bots/{id}/memory/corrections` | `{request_id, supersedes_seq, text}`. `201 {seq}`; a retry returns the same entry; `400 invalid_correction` when the target is not an owner entry of this bot. |
| `GET /v1/bots/{id}/memory-access` | Bots whose memory this bot may read. |
| `PUT`, `DELETE /v1/bots/{id}/memory-access/{target_id}` | Grant or revoke reading another bot's memory. A bot always reads its own. |

The summary tree (POC-014) is built inside the API by one compactor loop. Each entry gets a leaf job; a leaf whose labeled text (`Owner: …`, `Assistant: …`, `Owner correction of #N: …`, `Tool: …`) fits the node limit is copied verbatim, and two built siblings whose texts joined by a newline fit are joined into their parent. Anything longer is summarized by Codex with no tools at all (POC-015): an ephemeral thread in a separate per-bot home (`codex-summary`), no MCP server, the code-mode host and shell off, the saved Codex profile, and any tool, command, file, or agent item or server request rejecting the output. The prompt (`else-summary-v1`) treats records as data, keeps attribution, codes, and corrections, and gets the saved compaction view strictly before the range as context. One summary runs at a time, as its own task, so copies and joins for every bot continue meanwhile (other jobs that need a summary wait `waiting_for_summary` and are woken when it ends). Each attempt takes one of the `ELSE_MAX_ACTIVE_TURNS` provider slots only while no turn is queued and gives it back afterwards; turns reserve their slot before they are claimed, so turns and summaries together never exceed the limit. Output over the node limit is requested again (up to five attempts within 12 minutes, each told the measured size; the job's lease is 20 minutes) and is never cut; then the job waits `summary_oversized`, or `summary_failed` after an error, backing off by provider failures only (1 minute doubling to 1 hour); `waiting_for_capacity` and `summary_unavailable` (no provider) retry later without counting. Shutdown stops a running summary at once, reaps its process, and releases the job. Node audits record the recipe, sources, input hash, provider, model settings and profile revision, prompt version, attempt sizes, output bytes, and the context nodes and view revision. Jobs are claimed with a lease token that completion must present, so a worker whose lease was replaced cannot publish. Leaves publish into the saved view strictly in order after `published_seq`; above `view_high` bytes the view merges the adjacent sibling pair with the greatest `(count − last entry) / span` (oldest first on ties) until it is at most `view_low`, and only parents that exist merge, so a blocked parent never drops coverage. A second, smaller compaction view (16,000 to 32,000 bytes by default, scaled down for small recipes) covers the same prefix as summarization context; it takes the same leaves and also merges whenever the main view merges. Both views, the watermark, and the revision change together and are loaded unchanged after a restart. A saved view that fails to decode, does not cover its prefix, or names a missing node or generation is reported `valid: false` and left untouched; publication pauses for that bot. Publication takes at most 10,000 leaves per step and the idle compactor continues a longer backlog. Budgets (`node_bytes` 512, `view_high` 128,000, `view_low` 64,000, `context_high` 32,000, `context_low` 16,000 by default) are the installation recipe, recorded with each generation.

| Route | Behavior |
| --- | --- |
| `GET /v1/bots/{id}/memory/view` | The saved view: generation, revision, `valid`, published watermark, compaction state, jobs waiting by reason, the nodes with their text, and the compaction view's nodes (`context_nodes`). |
| `POST /v1/bots/{id}/memory/rebuild` | `202 {building_generation}`. Builds a new generation with the current recipe; appends meanwhile reach both. Once it has every leaf through the current log length (checked under the store lock), the API switches generation and both views atomically and keeps the old nodes. A leaf that still needs a summary keeps the rebuild open while the old view serves. |
| `GET`, `PATCH /v1/settings/memory` | The recipe for new generations: `{node_bytes, view_high, view_low[, context_high, context_low]}` (64 ≤ node ≤ 65,536; `view_low` ≥ 4 × node; `view_low` < `view_high` ≤ 4,000,000; node ≤ `context_low` < `context_high` ≤ `view_high`). |

Provider sessions reach memory over MCP at `POST /tools/v1/mcp` with their turn's task grant. Requests must be JSON-RPC 2.0 (`-32600` otherwise, `-32602` for bad tool parameters). `memory_view` pages through the saved view (`next_index`) with its covered and pending ranges and waiting jobs; `memory_zoom` opens a node into its halves (unbuilt halves are marked) or, for span 1, the original; node text cut by the response budget carries `truncated`, `text_bytes`, and `continue_with` (the halves, or the original with an offset); `memory_date` gives when entries were recorded. `memory_bots` lists readable bots (`more` when the budget cut the list); `memory_search` returns up to 20 hits (rank, then newest), each body at most 600 bytes, with a cursor bound to the log length at the first page, so corrections made later neither hide nor shift entries on later pages; `memory_read` reads up to 20 entries from a sequence number, gives `next_start_seq` when the budget stopped earlier, and pages a long entry with `offset` and `next_offset` (an offset inside a character starts at that character). Cut text is marked `truncated`, and at most ten correction links are listed per entry (`more_superseded_by`). Each complete tool result, sent once as JSON text, is at most 16,000 bytes after escaping. Appends lock the bot row before the memory store, so none lands after a deletion commits. Hits carry the originating bot, source IDs, authority, and correction links outside the text. Unknown, deleted, and unshared bots look the same. Each call is logged to the calling bot's memory as `tool_activity` (arguments and returned sequence numbers, not copied text). Deleting a bot keeps its memory and ends every read of it.

A Codex session that is new, or that never received memory, starts with the bot's saved memory (at most 24,000 bytes: the main view, else the compaction view, else its newest nodes with the omitted range stated, plus covered and pending ranges). The session records the view revision only after Codex accepts the turn (`provider_sessions.memory_revision`, migration `0009`), so a refused or interrupted delivery is retried with memory next time; a continuing session is not re-injected and uses the memory tools instead. If even one node exceeds the budget, the omitted range is stated. A summary whose thread reports different settings mid-turn is rejected as a profile mismatch.

### Delegation

The installation's main bot can hand one subtask at a time to another registered bot (POC-016). Its instructions (prompt `else-codex-v3`) list the registry of other active bots, by ID, name, and role, and the request's remaining budget; the registry is part of the session fingerprint, so a new bot starts a fresh session. Routing is the model's choice by role. The `delegate` MCP tool (`target_bot_id`, `task`) is granted only to attempts of the main bot's owner conversation and checks, in code: the caller is that conversation's running attempt, the target is another active bot, at most one child per attempt and two per owner request, and a retried call with the same task returns the same child. It returns `pending` with a `task_id` at once.

The child is an ordinary queued turn of the target bot in a separate task conversation (`conversations.kind = 'task'`): it never appears in the owner's chat with that bot or in its events, uses the target's selected provider (else Codex) and saved profile, and is numbered from the target's owner counter so the target's Stop covers it. Its task text enters the target's memory as `delegated_task` with assistant authority. A child cannot delegate, and its grant reads memory only from its own bot and from bots both the main bot and its own bot may read: delegation never inherits the target's other standing permissions. A retried call returns the same child only for the same task to the same target; a child that already ended is reported with its outcome, not as pending. After a pending result the parent attempt is parked: the API refuses its further tool calls (`409 attempt_parked`) and Codex interrupts it 20 seconds later if it keeps going, and ends the attempt 15 seconds after that if Codex does not report the end. Its owner turn becomes `waiting` (the bot shows working, its later messages wait, no provider slot is held). When the child's turn ends, by whatever path, a database trigger records the delegation's outcome and requeues the root; the next attempt resumes the native session with the recorded results as labeled data (`attempt` counts up); once Codex accepts that attempt the outcomes are marked delivered and logged to the main bot's memory as tool activity. Parking and child settlement serialize on the root turn's row lock (migration `0012`), and every path takes bot rows (main, then targets in ID order) before turn rows. A root that ends by restart reconciliation or orphan settlement stops its children. Stop work on the main bot cancels its pending children; deleting or stopping the target gives the parent a recorded cancellation to continue with.

### Bot computers

Each bot gets one persistent micro-VM, created on its first permitted use (POC-017). The API drives the pinned Microsandbox CLI (`msb` v0.7.13, found on `PATH`, at `ELSE_MSB_BIN`, or in `~/.microsandbox/bin`; another version is refused unless `ELSE_MSB_ALLOW_UNVERIFIED=1`, and its bundled `libkrunfw` must be present: `lib/libkrunfw.so.*` on Linux, `lib/libkrunfw.*.dylib` on macOS) with its own runtime home, `$ELSE_DATA_DIR/microsandbox`, so the owner's own Microsandbox state is never touched. Computers are named `elsebot-<bot id>`, use `ELSE_VM_IMAGE` (default `python:3.12-slim`; POC-018 builds the desktop image), and get 1 vCPU and 2 GiB (`ELSE_VM_CPUS`, `ELSE_VM_MEMORY_MIB`). No vendor login is involved, and provider CLIs, subscription credentials, and API secrets stay on the host. Each computer created by this API mounts the bot's host project directory (`$ELSE_BOTS_DIR/<bot id>`, by its resolved path: Microsandbox refuses a path through a symlink, such as macOS's `/tmp`) at `~/work` of the user that runs the bot's commands (`msb create --mount-dir`): `/home/elsebot/work`, owned there by `elsebot` (ID 1000), with the desktop image (`ELSE_VM_DESKTOP=1`), else `/root/work` as root. Files are shared live both ways between the bot's host runs and its computer, and the mount survives stopping and starting the computer. A computer created before that mount gets it only when recreated or upgraded. Checked on macOS 26.6 (Apple silicon) with `msb` 0.7.13 and `else-guest:2`, with and without the desktop.

`bot_computers` records the runtime name, image, resources, owner intent (`desired_state`: `auto` or `stopped`), the last established state, and a transition generation; `computer_leases` records renewable holders. Using a computer means acquiring a lease: under the computer's row lock the API creates, starts, or resumes it, or returns queued, owner-stopped, unavailable, or bot-inactive. Admission counts running, paused, and transitioning computers, each at its CPUs and memory plus `ELSE_VM_OVERHEAD_MIB` (256), against `ELSE_VM_MAX_CPUS` (2) and `ELSE_VM_MAX_MEMORY_MIB` (4,608), and queues beyond them. Runtime operations for one bot (create, start, resume, stop, pause, and commands) run one at a time; database decisions are taken under the row lock, and a start that finishes re-checks the bot and the owner's intent and stops the computer again if either changed. A failed transition is followed by inspecting the runtime and recording what it reports; when that is unknown the computer is `error`, keeps its budget reservation, and is inspected again by maintenance, which also retries an owner's or a deletion's stop until the runtime confirms it. Commands run only through a live lease on a running, owner-allowed computer (so a stopped VM is never woken by a command), and each of stdout and stderr is captured up to 1 MiB. Every 5 seconds the maintenance loop renews expired leases whose holder still works (a running turn) and releases the others (a renewal meanwhile wins), stops computers of deleted or owner-stopped bots, and stops (or, with `ELSE_VM_IDLE_ACTION=pause`, pauses) computers without leases after `ELSE_VM_IDLE_SECS` (600). A paused computer keeps its memory reservation; a stopped one releases its worker. Startup lists the runtime and records what it reports: it never wakes, creates, replaces, prunes, or removes a computer, and a recorded computer that is gone becomes `missing` rather than being recreated. No computer is used until that inspection succeeds; maintenance retries it. The singleton lock is held until the maintenance loop has stopped. Disks survive stop, restart, and soft deletion.

| Route | Behavior |
| --- | --- |
| `GET /v1/bots/{id}/computer` | Runtime name, image, resources, desired and observed state, active leases, last use and error (`absent` before first use). |
| `POST /v1/bots/{id}/computer/stop` | Owner stop: revokes leases, stops the computer, and blocks implicit wake. |
| `POST /v1/bots/{id}/computer/resume` | Clears an owner stop; the computer starts again only on next use. |

New computers use Microsandbox's `public` network profile (`ELSE_VM_NETWORK`): the internet is reachable, while the host, private ranges (including other bots' computers), and link-local metadata addresses are refused by the runtime's network policy.

#### Desktop image and guest tools

`infra/guest` defines the desktop image (POC-018): Debian trixie (base pinned by digest, packages from a fixed `snapshot.debian.org` date, `SNAPSHOT` build argument) with Chromium, Xvfb, Openbox, xterm, x11vnc, noVNC/websockify, and supervisord. `scripts/build-guest-image.sh [DATA_DIR]` builds it with Docker (tag `else-guest:2`, or `ELSE_GUEST_TAG`) and loads it into the API's runtime home; then set `ELSE_VM_IMAGE=else-guest:2` and `ELSE_VM_DESKTOP=1`. For a desktop computer the API picks a free host loopback port for noVNC and writes a random VNC password to a private host file (`$ELSE_DATA_DIR/computers/<bot>/vnc.pass`, 0600) that is copied into the guest at creation. On the first use of each boot it runs `else-init` (recorded per generation as `services_generation` and retried on a later use if it failed; the owner's desktop is offered only once it succeeded), which starts supervisord as a daemon (the runtime's agent stays PID 1, so its graceful stop works) and is a no-op while the services run. Before stopping a running desktop it runs `else-checkpoint`, which closes Chromium cleanly so its profile is flushed and unlocked. VNC listens on guest loopback only and requires the password; Chromium's DevTools listens on guest loopback only and is never published; noVNC is published on host loopback only.

#### Guest programming toolchain

`else-guest:2` (POC-025) adds a programming toolchain from the same Debian snapshot (`20261101T000000Z`) and base digest, so a rebuild installs the same versions: Node.js 20.19.2 with npm 9.2.0, Python 3.13.5 with pip 25.1.1 and venv, Rust and Cargo 1.85.1, Git 2.47.3, GCC/G++ 14.2.0 and the C library headers, make 4.4.1, pkg-config, jq, curl, tar/gzip/bzip2/xz/zip/unzip, GNU time, and CA certificates. Chromium stays 156.0.8078.73. (The POC-018 image already contained `nodejs` as a noVNC dependency, but not npm, Cargo, rustc, pip, or a compiler.) `/etc/elsebot/image.json` records the tag, snapshot, and exact package versions; `else-capabilities` prints it with the live tool versions as JSON, and the `computer_run` tool description points bots at it. The image `PATH` holds only root-owned directories, and root commands the API runs (`/usr/sbin/runuser`, `else-init`, `else-checkpoint`, the upgrade scripts) use absolute paths or that trusted `PATH`; the bot's own commands and jobs get `~/.cargo/bin` and `~/.local/bin` prepended only after the switch to `elsebot`, so the unprivileged user runs every tool from a plain non-login shell and nothing it writes can shadow a root command. Projects, virtual environments, `node_modules`, `~/.cargo`, and other caches live in the guest under `/home/elsebot`; no provider CLI, credential, or runtime socket is installed. Python packages go in a venv (Debian marks the system Python as externally managed).

Measured on this host (`toolchain_live`): the image is 2.7 GB unpacked (690 MB compressed) against 1.57 GB for `else-guest:1`, and a fresh build from the snapshot took 854 s, mostly package downloads. A computer's exported disk with its image was 615 MiB after the test projects. A computer boots and answers `else-capabilities` in about 1.2 s. With the default 1 vCPU and 2 GiB, a Rust release build of `serde` + `serde_json` with derive took 15 s with 331 MB peak RSS, 35 MB of `target` and 9.3 MB of Cargo registry; installing `ms` with npm and `six` in a venv took seconds. The guest root filesystem is a 3.9 GB overlay (Microsandbox's default root disk), so large dependency trees, toolchains installed with `rustup`, big `target` directories, or datasets need a larger root disk and memory than the desktop budget. Builds of large crates or with parallel jobs need more than 2 GiB; set `ELSE_VM_MEMORY_MIB` and `ELSE_VM_CPUS` for new computers.

New computers use the configured image; an existing computer keeps the image it was created with, and startup never replaces its disk or resets its profile. `else-api upgrade-computer <bot-id> <image> [--network <profile>]` (with the API stopped; it takes the singleton lock) moves one computer to a new image. It first ends leases the stopped API left (turns and desktops cannot be live without it) and asks the guest about running jobs, so a job that finished meanwhile is recorded; it refuses while a guest job is still active, stops an idle one through the normal stop (checkpointing Chromium), boots the stopped disk without its desktop services to archive `/home/elsebot` (projects, environments, caches, the browser profile; a mounted project directory is another file system and stays out, while an older computer's on-disk `~/work` is unpacked into the new computer's mount, moving it to the host project directory) and `/var/lib/elsebot` with numeric owners, verifies the copy on the host by size and SHA-256 (the archive keeps sparse files sparse, needs free space on the old disk for itself and on the new disk for the unpacked data, and is removed from the old computer on success and failure), creates a new computer `elsebot-<bot>-<id>` from the new image with the same resources, desktop port, VNC password, and network profile (recorded per computer since migration `0023`; a computer created before that needs `--network public` or `--network none`, and `--network` is the explicit way to change it), checks the guest user ID matches, verifies and unpacks the archive there, and stops it. Only then does the bot switch to it (`computer_upgrades`, migration `0022`). The old computer is kept stopped. `else-api rollback-computer <bot-id>` switches back to it (work done since the upgrade stays in the newer computer, also kept). Each boot (the old computer to read it, then the replacement) is admitted against the computer budget like any start, and refused when it is full. A failure before the switch removes only the replacement and leaves the bot on its old computer; an interrupted upgrade's replacement is stopped by the next API startup and removed by the next attempt, even for a deleted bot. `else-init` clears Chromium's stale profile lock before starting it, since a copied profile's lock names the old computer's hostname. Removing kept computers is a manual step (`MSB_HOME=$ELSE_DATA_DIR/microsandbox msb rm <name>`).

`ELSE_LIVE_VM=1 cargo test -p else-api --test toolchain_live -- --nocapture --test-threads=1` checks all of this against real VMs (it needs `else-guest:1` and `else-guest:2` built and downloads small packages from npm, PyPI, and crates.io).

#### Recovery and Stop work

#### Desktop screenshots

`computer_screenshot` (POC-028) shows the model the bot's whole desktop: the Xvfb display `:99` (1280x800) that x11vnc serves to the owner, every window, not only the browser. Inside the guest, `else-screenshot` reads the root window through libX11 (`ctypes`, no extra packages), encodes a PNG with `zlib`, and reports the screen size, image size, scale (screen pixels per image pixel), pointer position, size, SHA-256, and time; a PNG over the 1.5 MB image budget (separate from the 16 KB text budget, and well inside the providers' 8 MiB event lines) is reduced by 2, 3, then 4, then refused as `IMAGE_TOO_LARGE`. The API captures under the turn's lease and the computer's operation lock (so an owner-stopped computer is `COMPUTER_STOPPED` and never started), and only if the turn still runs once the lock is held (a capture queued behind other work for a turn stopped meanwhile is `STOPPED`). The desktop user writes the PNG; root then takes a copy bounded by the budget (`dd iflag=nofollow,count_bytes`, regular files only) into `/var/lib/elsebot-screens`, which only root writes, and that copy is what leaves the guest, so a swapped or oversized file cannot reach the host. Each capture first clears what an interrupted one left in the guest and the host staging directory, and every exit removes its own files (a failed artifact registration removes the stored file). The API verifies the PNG header size and SHA-256 against the capture; the result is an MCP `image` content block (`image/png`, base64) after a text block with the metadata, so the provider receives pixels. Tool activity records the metadata only (capture ID, sizes, scale, bytes, artifact ID), never image data. `save: true` keeps the PNG in the bot's artifact store (`guest_path` `screen:<id>`) with its capture metadata (`artifacts.meta`, migration `0026`), covered by encrypted backups like other artifacts and kept until the artifact store is purged; otherwise no copy remains on the host or guest. `artifact_id` shows a saved screenshot again with its original metadata (screen size, scale, pointer, capture ID and time, so image coordinates still map to the screen): only this bot's, only a screenshot, and only if its bytes match the recorded SHA-256 (anything else is "No such screenshot"). The tool is annotated as not read-only (it may start the computer and store an artifact). The decoder accepts only the 32-bit LSBFirst xRGB format Xvfb provides and refuses others. Image data lives in else.bot only transiently; the providers' own native session transcripts (in each bot's private provider home, never backed up) can keep it as part of their conversation, as the live check observed for Claude. Only models verified to receive MCP images may capture (`VISION_MODELS`: `gpt-6.1-sol`, `claude-haiku-5-5`, `claude-sonnet-5-5`, `claude-opus-5-5`); another model gets `IMAGE_UNSUPPORTED` with nothing captured, and nothing switches models. A missing display is `DISPLAY_UNAVAILABLE`, a mismatched copy `SCREENSHOT_INVALID`, a computer without a desktop says so. `cargo test -p else-api --test screens` covers these outcomes against a fake runtime; `ELSE_LIVE_VISION=1 cargo test -p else-api --test vision_live -- --nocapture` has Codex and Claude read a random code word drawn only into pixels.

#### Pointer and keyboard input

`computer_input` (POC-029) operates the same desktop: a batch of 1 to 20 actions in screen pixels (`move`, `click` with button and count, `drag`, `scroll` by wheel steps, `key` for a key or chord pressed together such as `ctrl+l`, `Enter`, or `%` with the Shift it needs, `type` for literal text with Caps Lock neutralized and restored, `wait`), plus `frame`, the screen size from the latest screenshot. Inside the guest, `else-input` drives XTest on display `:99` through `ctypes` (libX11 and libXtst, no packages); it never addresses another display, and there is no clipboard action. The batch reaches it in an environment variable sent over the runtime's stdin (the task-secret path), never in a command line, and the output filter keeps it out of the guest's output files; errors name the action number and the reason, never the supplied values. Before anything happens it resolves every key name and checks every point, takes the desktop lock that CDP scripts and `computer_browser` take (`DESKTOP_BUSY` after 20 seconds), and then requires the screen to still be `frame` (`SCREEN_CHANGED`: take a new screenshot) and no VNC viewer to be connected to x11vnc (`OWNER_USING_DESKTOP`); only then does it report that it started, and a refusal before that did nothing. Before each action it checks the screen size and VNC connections again and stops if either changed. A press is recorded before it is sent, with SIGTERM blocked around each event, so whatever it pressed is released at the end, on an error, and on SIGTERM; every guest kill also runs `else-input --release-all`, which releases every key and button X reports as held, so a forced kill leaves nothing pressed either. Characters the keyboard lacks go on keycodes with no mapping at any level, one per symbol, all restored to empty. In the API the batch runs as a registered foreground command through a dedicated path that, under the computer's operation lock, refuses if the turn is no longer running (`STOPPED`, so a batch queued behind other work does not run after Stop work) or if the owner's desktop lease is open (desktop admission takes the same lock, so the two exclude each other). Owner stop ends a running command before waiting for that lock, the orphan loop also ends commands of owner-stopped computers, and a dropped request ends its turn's commands. Any outcome after the batch started that is not a clean finish is `UNCERTAIN` with the number of completed actions and is never replayed. A turn may send at most 40 batches (`INPUT_LIMIT`; the bot then reports to the owner). Tool activity records action kinds and points, never typed text (`type(16 chars)`). `cargo test -p else-api --test screens` and `--test task_secrets` cover these outcomes against fake runtimes; `ELSE_LIVE_INPUT=1 cargo test -p else-api --test input_live -- --nocapture` checks the helper directly and has a Codex bot complete visual web tasks and type into a terminal window. The screen is a fixed 1280x800 Xvfb; resizing is handled by refusal and a new capture, not exercised live.

#### Browser scripts over CDP

Chromium's DevTools endpoint stays on guest loopback (`--remote-debugging-address=127.0.0.1 --remote-debugging-port=9222`, never published by the runtime, which maps only noVNC), and bot scripts drive the same visible browser through it (POC-027). The image ships dependency-free helpers in `/usr/local/lib/elsebot/cdp`: `cdp.mjs` for Node.js (`import { connect } from "/usr/local/lib/elsebot/cdp/cdp.mjs"`) and `elsecdp.py` for any Python 3, including a virtual environment (`sys.path.insert(0, "/usr/local/lib/elsebot/cdp")`), each with its own minimal WebSocket client, plus `example.mjs` and `example.py`; `else-capabilities` lists them under `browser` with whether DevTools answers. The helpers connect only to `127.0.0.1:9222` (any other endpoint is refused) and no API tool takes an endpoint. `connect()` waits for the browser (bounded) and takes the browser lock `/var/lib/elsebot/browser.lock` (`flock`), which `computer_browser` also takes, so one controller drives the browser at a time; the tool waits 20 seconds for a script and then reports `BROWSER_BUSY`. The lock belongs to the script's process, so ending the script (Stop work, `computer_job_cancel`) releases it. `browser.page()` attaches to a tab by ID, URL prefix, or title, or creates one (`Target.createTarget`) and brings it to the front, so the owner sees it over VNC. Nothing that runs in a page is ever sent twice: a reply lost to a timeout or a closed connection raises `Uncertain` for an action (`navigate`, `click`, `fill`, `evaluate`, `show`) and `TargetClosed` or `CdpError` for `read`, which marks an expression the script considers side-effect free but does not resend it either (page getters can have effects). A navigation whose server never answers raises `NavigationTimeout`; completion is tied to the requested navigation's new document, so `about:blank` works. `reconnect()` reattaches only to the same target ID and otherwise fails with `TargetClosed`; a browser restart gives tabs new IDs, so the script opens the page again and checks it. Page code runs under a browser-side limit (`Runtime.evaluate`'s `timeout`, at most 300 seconds). The helpers record the tabs a script controls in `/var/lib/elsebot/browser-controlled.jsonl`; every guest kill (Stop work, `computer_job_cancel`, a timed-out command) then runs `else-browser reconcile`, which closes the tabs a script that no longer runs opened (pending timers and requests in them end with the tab) and tries to halt code in tabs it attached to (`Runtime.terminateExecution`); a page busy in a loop cannot be attached to, so that code ends at its own limit. All of this happens before the job's or command's end is recorded and its lease released. Scripts run through `computer_run` or background jobs, so their work holds the computer's lease, and a running script defers a backup like any held computer; the backup's stop still checkpoints Chromium. Verified with Chromium 156.0.8078.73 (Debian): remote debugging works with the explicit `--user-data-dir=/home/elsebot/.config/chromium`, so no profile migration was needed. Direct DevTools clients that bypass the helpers are not serialized; the bot is told to use the helpers. `ELSE_LIVE_VM=1 cargo test -p else-api --test cdp_live -- --nocapture` runs the checks against a real VM with the fixture `apps/api/tests/fixtures/cdp_site.py`.

#### Scripts and task secrets

Bots write and run their own code in their computers (POC-026). The instructions (prompts `else-codex-v9` and `else-claude-v6`) describe the workflow: a directory under `~/work` (the bot's project directory, shared with the host) per task, files written with `computer_write_file`, a runtime chosen from `else-capabilities`, dependencies installed in the project (a venv for Python), quick steps with `computer_run` and long ones as background jobs checked with `computer_job`, results returned with `computer_fetch`, and the source location reported to the owner. Work with side effects keeps receipts per item (`sent` only after the server confirmed it, `failed`, or `uncertain` when the outcome is unknown); a repeated request reads them and skips what was sent, an uncertain item is never resent without the owner's explicit confirmation, and an explicit request for a whole batch runs once without per-item questions. Stable message IDs alone are not treated as exactly-once delivery.

Credentials a script needs are task secrets the owner stores per bot: `PUT /v1/bots/{id}/task-secrets/{name}` with `{"env": {"SMTP_PASSWORD": "..."}}` (1 to 16 variables, values up to 4,096 bytes; names in `A-Z0-9_`, not `PATH`, `HOME`, `LD_*`, `ELSE_*`, or other variables that change how a command runs), `GET /v1/bots/{id}/task-secrets` (names and variable names only), and `DELETE`. `task_secrets` (migration `0024`) stores each secret age-encrypted with a key derived from `SECRET_KEY` and a per-secret salt (purpose `else.bot/task-secrets/v1`); a backup set carries them encrypted, and its restore copies the master key. Task grants cannot reach these routes. The bot sees names through `computer_secrets` and passes `secrets: [names]` (up to 4) to `computer_run` or `computer_job_start`; a name that is not its own bot's is `SECRET_UNKNOWN`. The API decrypts them for that one call and sends them on the runtime's stdin (`msb exec` forwards it) as `NAME BASE64` lines that the guest script exports before running the command, so a value never appears in a command line, a file, saved source, or the tool-activity log (which records the secret names). The guest script exports each value exactly as sent (a trailing newline survives the decoding). Output that would show a value never reaches a file the API manages: when secrets are sent, the command's stdout and stderr (and a job's combined output) pass through a small filter inside the guest that replaces every value with `[secret NAME]`, holding back only enough bytes to catch a value split across reads, so `/var/lib/elsebot/jobs/<id>/out` and the foreground temporary files never hold one, and `computer_read_file` or `computer_fetch` of them cannot reveal it. The API redacts again before returning or storing a tail, reading 4 KiB more than it keeps so a value cut by the tail boundary is seen whole first. Nothing derived from a value is stored (a stored fingerprint of a short value could be brute-forced without `SECRET_KEY`): a job records only the names of its secrets, and the API decrypts them again when it redacts the job's output. Values shorter than 4 bytes are not redacted, and the store response lists them. A script that deliberately transforms a value (for example base64) or writes it to a file of its own can still reveal it; the guard is against accidental echoes.

Foreground commands run in their own session with their process group recorded in `/var/lib/elsebot/runs/<id>` together with the guest boot ID, so no kill after a reboot can target a reused process ID; whatever a command leaves running in its group is ended when it returns (long-lived processes belong in background jobs). The tool layer runs each command in a task of its own, so a dropped request cannot cut it off, and the command holds its bot's operation lock from before it is recorded until after it is retired. It is recorded in `guest_runs` (migration `0025`) and in memory. A command whose runtime call failed or hit its timeout is killed, and confirmed gone, before it is retired (Microsandbox's timeout ends only the wrapper's group). A separate loop every 2 seconds ends commands whose turn is no longer `preparing`, `sending`, or `running` or whose bot is no longer active: one this process runs is killed without the lock it holds (so its computer runs), only while still registered; one an earlier API process left is killed under the lock if its computer is still running in the same boot. Each kill runs in its own task and a pass waits at most 10 seconds, so one unresponsive computer delays no other bot. Stop work and deletion settle only once no foreground command of the bot is recorded as running, so a stop receipt is not `done` while a script still runs. Measured: Stop work ended a foreground command and a job in about 4 seconds; a command left by a killed API ended within seconds of the restart.

`ELSE_LIVE_SCRIPTS=1 cargo test -p else-api --test scripts_live -- --nocapture` runs the scenario against the real binary, Codex, and `else-guest:2` (see `docs/implementation/progress.md` for the observed run); `apps/api/tests/fixtures/smtp_capture.py` is its capture-only SMTP server, which runs in the guest on loopback, requires a login, delivers nothing, and can drop the acknowledgment for one recipient. `cargo test -p else-api --test task_secrets` covers storage, scoping, stdin delivery, Stop work ending a foreground command (with the stop pending until it ended), and a stalled kill not delaying another bot, against a fake runtime; `cargo test -p else-api --test guest_scripts` runs the real guest shell scripts and filter on the host in a private home (exact values including a trailing newline, filtered foreground output and job files, a long value at the tail boundary, a timed-out command and its descendants ended, leftovers in a command's group ended).

Bot-wide Stop work and deletion also cancel the bot's background guest jobs (POC-019): under the bot row lock they become `cancelling`, and maintenance kills each one's process group under the bot's operation lock, without needing a lease or an active bot (asking the guest never wakes a computer; a paused one is stopped instead). A job is recorded `cancelled` only once the guest confirms its group is gone, or `lost` once its computer is confirmed stopped; until then it keeps its lease, which maintenance renews. The stop receipt stays `pending` until no turn and no job remains active, and a deleting bot stays `deleting` until, in addition, its computer is confirmed stopped. Every maintenance pass settles such bots, whichever path ended their last work. Job admission is fenced the same way: a slot is reserved under the bot row lock only while the bot is active and the originating turn still runs (or, without a turn, no stop is pending), and the launch runs under the operation lock only while the job is still `starting`. A launch whose reply is lost or cut off stays `starting` with its lease; after 120 s maintenance looks at its guest directory and records it running or `lost`. Host provider capacity (`ELSE_MAX_ACTIVE_TURNS`) and VM capacity (the computer budget) are counted separately; measured on this host an idle Codex app-server uses about 300 MB RSS while the VM worker for an idle guest uses about 126 MB RSS outside its configured guest memory. Crash points are tested with named fault points (`faults::arm`): `computer.after_start_decision`, `computer.after_stop_decision`, `lease.after_renew`, `job.after_insert`, and `job.after_launch` make the operation return `interrupted` right after the step, and a fresh `ComputerManager` stands in for the restarted API. `cargo test -p else-api --test recovery` runs them against a fake runtime; the live race of acquisition against owner stop and deletion is `ELSE_LIVE_VM=1 cargo test -p else-api --test computers_live races`.

Live checks boot real VMs and run only on request: `ELSE_LIVE_VM=1 cargo test -p else-api --test computers_live -- --nocapture` (the guest test needs `docker build -t else-guest:1 infra/guest` first).

### Updates

The installer prepares a running API before it switches releases with `POST /v1/maintenance/update` (owner only): it closes the maintenance gate (below), so no turn, mutation, tool call, or memory step is admitted and queued messages stay queued, and then refuses with `409 busy`, reopening the gate, while a turn is active or a command runs in a bot computer. Otherwise the gate stays closed until the process exits, so nothing starts between that answer and the shutdown; background jobs are reported and keep running across the restart. `DELETE /v1/maintenance/update` reopens the gate for an abandoned update. Both bypass the gate themselves. `/healthz` reports the version, as do `else-api version` and `else-desktop --version`. See [Update](../README.md#update) for the installer's side, and `apps/api/tests/update_gate.rs`.

### Backups and restore

The API runs one backup worker (POC-021). Every `ELSE_BACKUP_INTERVAL_SECS` (86,400 by default; `0` turns the schedule off) it captures an encrypted database set into `ELSE_BACKUP_DIR` (`$ELSE_DATA_DIR/backups`, mode 0700) and keeps the newest `ELSE_BACKUP_KEEP` (7) completed sets. A missed set runs once at startup, not once per missed interval; a failure is retried after 1 minute, doubling to at most an hour. `else-api backup` captures one set now. A file lock on `<backup dir>/.lock` (released by the kernel if the process dies) serializes capture, retention, and cleanup between the API's worker and manual runs, and each run first removes leftovers of interrupted runs under it. Shutdown kills and reaps a running `pg_dump` rather than abandoning it. Runs are recorded in `backup_runs` (migration `0018`) with separate local and remote status, the error, the encrypted size, and the coverage.

A set `<set id>/` (a UTC timestamp with a random suffix) holds `database.dump.age` (a `pg_dump --format=custom --no-owner --no-acl` dump streamed from `pg_dump`'s stdout through age, never written in plaintext, at most `ELSE_BACKUP_MAX_BYTES`, 8 GiB by default), `manifest.json.age`, and, published last, `complete.json`. Each is a separate age (`age-encryption.org/v1`) encryption for an X25519 identity derived per set from `SECRET_KEY` with HKDF-SHA-256, a fresh public 32-byte salt, and the purpose `else.bot/backups/v1`. `complete.json` is the unencrypted bootstrap: schema version, set ID, the encryption fields (format, KDF, purpose, salt, and an opaque key ID derived one-way from the master key), and the manifest's size and SHA-256. The manifest records the times, application and migration versions, PostgreSQL and `pg_dump` versions, extensions, every artifact's sizes and SHA-256 before and after encryption, every table's row count and content digest, the bots, and the coverage. The digests (per table, a SHA-256 streamed over the sorted row hashes, so no table is aggregated in memory) and the dump use one exported snapshot, so they describe exactly the dumped rows. These sets are database only: `coverage` marks bot computers and provider state as omitted and `whole_assistant` as false. The set is staged under `.staging-<id>`, every file and directory synced, renamed into place without replacing anything, and only then is `complete.json` linked in (never replacing one). Each set and staging directory gets an ownership marker (`.else-backup`) when created. A failed `pg_dump`, an encryption error, an oversized dump, or an interruption leaves no completed set; staging and unfinished sets are removed at the next run, and only real (not symlinked) directories carrying the marker are ever removed, so completed sets and anything else placed in the backup directory are never touched. Retention orders sets by completion time, always keeps the set just published, and removes a set's `complete.json` before the rest. Connections use SQLx's own parse of `DATABASE_URL` (query overrides such as `host=` or `dbname=`, sockets, IPv6, and the TLS mode and certificate files apply to every connection), and `pg_dump` and `pg_restore` get the matching libpq environment; the database password reaches them only through that environment, and their output is drained with bounded tails (`ELSE_PG_DUMP`, `ELSE_PG_RESTORE` select the binaries, `pg_dump` and `pg_restore` on `PATH` by default; use the server's major version). A missing `SECRET_KEY` is an error; nothing generates one.

`else-api restore <set-dir> <new-database>` restores into a new database on the server of `DATABASE_URL`, with the API stopped, and changes nothing existing. It refuses a set without `complete.json`, an unknown format or schema, a key whose ID differs (`this set was made with key …`) before decrypting anything, and any size or hash mismatch of the manifest or dump, and decrypts the dump (at most `ELSE_BACKUP_MAX_BYTES`) through its authenticated end into a private staging directory under `$ELSE_DATA_DIR/restore-staging` that is removed afterwards. One restore runs at a time per staging directory, under a lock that also removes staging left by a killed restore. An existing target database is refused untouched. The new database is created from `template0` and loaded with `pg_restore --single-transaction --exit-on-error --no-owner --no-acl`; then every table must match the manifest's counts and digests and its migration state, newer migrations are applied, and every restored provider profile must still pass its adapter's rules (so a restored setting cannot enable native sub-agents, such as Codex's `ultra`). If any step fails, the database the restore created is dropped. Point `DATABASE_URL` at the new database to use it.

#### Coordinated assistant sets

The API's worker captures the whole assistant at one checkpoint (POC-022). Work that can change state or wake a computer is admitted through a maintenance gate and holds its admission until it ends: each turn claim (until the turn is registered as running), every `/v1` request other than reads, Stop work, and stopping a computer (opening a desktop is admitted work), every `/tools/v1` call, each memory summary, and each compaction step. Closing the gate refuses new admissions (`503 maintenance`) and waits for admitted work to end; then active turns drain. Both get up to 300 seconds together, or the set is deferred and retried. Then, for every active bot, under the computer's operation lock: an idle running computer is checkpointed (a desktop's `else-checkpoint` must succeed, closing Chromium cleanly; a paused desktop is resumed for it) and stopped through the normal stop, a stopped one, including an owner-stopped one, is captured without being started and relies on the checkpoint recorded when it last stopped (`bot_computers.browser_checkpoint`, migration `0019`), and a computer still held by a lease (a background job or an open desktop) or in transition defers the whole set. A turn's lease lasts until it expires (5 minutes) after the turn ends; whole-disk operations (backup capture and image upgrades) end the leases of turns and jobs that are no longer running instead of waiting for that (POC-032), while leases of live work and of any other holder still defer. Each disk is captured as a verified Microsandbox disk snapshot of the stopped computer and exported as a standalone archive with its image (`msb snapshot create`, `verify`, `export --with-image`; the snapshot is then removed from the runtime home), sealed into `vm-<bot>.msb.age`, and its plaintext removed. Host artifacts the bots fetched (`$ELSE_DATA_DIR/artifacts/<bot>/<id>`) whose size and SHA-256 match their rows are sealed as `file-<id>.age`. Each active bot's project directory (`$ELSE_BOTS_DIR/<bot>`, quiescent now: no turn runs and its computer, which mounts it, is stopped) is archived as a plain tar and sealed as `project-<bot>.tar.age`: regular files, directories, and symbolic links (never followed) with their modes and modification times; sockets, FIFOs, and devices are skipped. An entry that cannot be read is left out and logged, and the bot's `project` is then `partial`; a bot without a directory is `none`. Project directories are captured at the checkpoint even without Microsandbox (`else-api backup` on a host without `msb`), and the set then says it holds the database and the project directories only. The database snapshot and dump follow, so the database records the computers as stopped; the gate reopens once the dump is fixed. A desktop computer without its VNC password fails the capture. The manifest records, per bot, its computer (`included`, `none`, `missing`, or `omitted-deleted-bot`) with its runtime name and version, image, resources, the owner's intent, network profile, desktop port and VNC password, whether it was running, its project mount (guest path and owner, read from `msb inspect`; absent for a computer created before project mounts), its project state, and its native provider sessions (not included: `omitted-reauth-required`). `coverage.whole_assistant` is true only when every active bot's computer is included, every desktop's browser checkpoint is `ok`, every active bot's project directory is included whole (`coverage.projects`), and every host artifact is included; otherwise the set is `partial`, and any failed capture or export publishes nothing. `complete.json` repeats the whole-assistant flag as a retention hint: retention never removes the newest whole-assistant set, so a partial set cannot replace the last full recovery point. Each set is standalone, so retention, which removes whole sets, never removes an artifact a kept set needs.

`else-api backup` now takes the API's singleton lock before migrating anything (it refuses while the API runs, which backs up on its own schedule) and captures the computers too when Microsandbox is available. `else-api restore <set-dir> <new-database> [<new-data-dir>]` restores a set with computers or host artifacts only into a new installation directory, created exclusively (an existing path, including one a concurrent restore just made, is refused) and given a copy of the master key and a new owner token before anything is restored: each archive is verified and decrypted to private staging, restored into `<new-data-dir>/microsandbox` with its recorded resources and desktop port and an explicit network policy (`msb snapshot restore` does not carry the source's; `public` becomes default deny with DNS and public egress allowed and ingress allowed, the policy `create --net public` records), and left stopped; the desktop password and host artifacts are written to the new directory. The restored database then records the restored computers as stopped, any computer not in the set as `missing` (never recreated), every native provider session as retired (conversations are rebuilt from PostgreSQL; providers may need a fresh login on a new host), memory job leases as released, and the run that made the set as completed. If anything fails, every computer the restore tried to create is stopped and confirmed stopped, and the new database and directory are removed; if a stop cannot be confirmed, the directory is kept and the error says so. Point the API at both to switch over. Project directories are unpacked first into `<new-data-dir>/projects/<bot>` (absolute paths, `..`, hard links, special files, and anything that would land outside the directory through a link are refused; nothing is overwritten), and a computer captured with a project mount is restored with that directory bound at the same guest path and owner (`msb snapshot restore -v`). The restore prints the directory: point `ELSE_BOTS_DIR` at it, and keep it there, since restored computers mount it by path. A set with project directories but no computers restores without Microsandbox; one with computers needs it. Sets made before project directories restore as before.

#### Bucket replication

With `ELSE_S3_ENDPOINT`, `ELSE_S3_BUCKET`, `ELSE_S3_ACCESS_KEY_ID`, and `ELSE_S3_SECRET_ACCESS_KEY` set (and optionally `ELSE_S3_REGION`, default `auto`; `ELSE_S3_PREFIX`, default `else-backups/`; `ELSE_S3_PATH_STYLE`, default `1`), the backup worker replicates every completed local set to the bucket after each capture, in the same process and under the same lock (POC-023). It uses a small Signature V4 client and only the operations the emulator probe verified: `PutObject` (with a SHA-256 checksum, and `If-None-Match: *` for the completion record), multipart create, upload, complete, list, and abort, `HeadObject`, `GetObject`, `ListObjectsV2`, and `DeleteObject`; no AWS endpoint is assumed. Objects go to `<prefix>sets/<set id>/`. For a set not yet verified at this destination (endpoint, bucket, and prefix; state is kept per destination, so a new bucket is replicated afresh) it aborts that set's abandoned multipart uploads, uploads the manifest and every artifact (objects over 16 MiB in parts), skipping any whose remote readback already hashes to the recorded SHA-256, then reads every object back again and compares its SHA-256, and only then publishes `complete.json` create-only and reads it back. An existing completion record identical to the local one is accepted only after the same verification (and repair) of every object it refers to. A mismatch fails the set (it is not marked remotely complete and is repaired on a later pass); a remote completion record with other contents is a conflict and is never replaced. Local and remote outcomes are recorded separately (`backup_runs.remote_status`, `backup_remote`, migration `0020`); a remote failure leaves the local set complete and is retried with backoff (1 minute, doubling to an hour) without capturing again; captures keep their own schedule, so an outage never stops local backups, and sets left awaiting upload are uploaded as soon as the worker starts. Requests have a 120-second idle timeout rather than a total one, so large archives stream as long as data flows; the signed host is exactly the transmitted one (lowercase, default port omitted). Local retention never removes a set awaiting replication. Remote retention counts only sets this installation verified at this destination: it keeps the newest `ELSE_BACKUP_KEEP` of them (never fewer than one) and the newest whole-assistant one, removes older ones completion record first (they are then `retired` there and not uploaded again), never touches a set whose completion record it did not verify, and removes incomplete remote sets that no local set awaits.

`else-api restore-remote <set-id> <new-database> [<new-data-dir>]` downloads a completed set using only the bucket settings (the configured database need not exist, as on a replacement server): the completion record, the manifest (refused if declared larger than the manifest limit), and the objects the decrypted manifest names, each refused if declared larger than `ELSE_BACKUP_MAX_BYTES` allows and bounded by its declared size, into `$ELSE_DATA_DIR/restore-download`, restores it exactly like a local set, and removes the download.

### Events and reconnecting

Every change to history or turn state appends rows to `bot_events` in the same transaction, under the bot's row lock, so a bot's event sequence follows commit order. Cursors are `<server_instance_id>:<bot_id>:<seq>`; the instance ID changes on every API start. The socket sends only committed rows; inside the API, channels wake on a `pg_notify` hint or a one-second database poll. `item.delta` carries `offset_utf8`, the byte length of the item's text before the delta; a client appends only when its current length matches.

Live updates use one WebSocket at `GET /v1/ws`, authenticated like every other route. Commands stay on HTTP because they carry request IDs and status codes. Messages are JSON:

```text
→ {"op":"subscribe","channel":"bots"}
→ {"op":"subscribe","channel":"bot:<id>","cursor":"<cursor from a snapshot>"}
→ {"op":"unsubscribe","channel":"bot:<id>"}
← {"channel":"bots","event":"bots.snapshot","data":{"default_bot_id":…,"bots":[…]}}
← {"channel":"bot:<id>","id":"<cursor>","event":"item.delta","data":{…}}
← {"channel":"bot:<id>","error":{"code":"cursor_reset_required","message":"…"}}
```

`bots` pushes the whole list on subscribe and whenever a bot is created, deleted, or changes activity. Clients take a snapshot, subscribe to `bot:<id>` with its cursor, apply only the next contiguous `seq`, ignore IDs at or below the applied one, and after a reconnect resubscribe with the last received cursor. Channel errors end only that channel: `cursor_required` or `invalid_cursor` (malformed or another bot's), `cursor_reset_required` (earlier API process or beyond the latest event; load a fresh snapshot), `bot_deleted`, `not_found`, and `unavailable` (a database read failed; resubscribe). Every subscription ends with an error or an unsubscribe, never silently, and nothing queued by a replaced or unsubscribed subscription is written. Deleting a bot ends its channel within about a second with `bot_deleted`, and the snapshot then returns `410 bot_deleted`. The server pings every 15 seconds; a connection allows 32 running channels and shares one bounded outgoing queue among them. Event payloads contain no request hashes, profiles, native session IDs, or credentials.

The first version used a per-bot SSE route and three-second sidebar polling; the [desktop contract](research/desktop-and-feature-contracts.md#history-sse-and-polling-were-tried-first) explains the switch.

### Database and migrations

Versioned SQL migrations live in `apps/api/migrations` and are embedded in the binary. Applied versions are recorded in `_sqlx_migrations`, so applying them again is a no-op. Apply them explicitly with:

```sh
cargo run -p else-api -- migrate
```

`serve` and `setup` also apply pending migrations before doing anything else. `serve` then requires completed setup: on an empty installation it exits with `installation setup has not completed; run else-api setup` and creates nothing. An unreachable database fails startup within five seconds with `cannot reach PostgreSQL`. `GET /healthz` reports process liveness; `GET /readyz` returns `200 {"status":"ready"}` while PostgreSQL answers and `503 database_unavailable` otherwise. Neither requires authentication or returns data.

Migrations never delete or rewrite saved rows to make startup succeed. The saved Codex profile is seeded as `gpt-6.1-sol`, `medium`, `priority` only when its row is missing.

### Credentials

The API has three independent kinds of credential. Do not substitute one for another.

| Credential | Holder | Authority |
| --- | --- | --- |
| Owner token | The desktop and trusted owner tooling | Every `/v1` route, sent as exactly one `Authorization: Bearer <token>` header. The API keeps only its SHA-256 digest and compares in constant time. |
| `SECRET_KEY` | The API process only | Encrypts recoverable secrets and backups in later tasks. It authenticates no request. |
| Task grant | One restricted provider session, in a later task | Its own bot, conversation, and tool allowlist. It cannot use owner routes. Not implemented yet. |

The examples pipe the header through `printf`, a shell builtin, so the token never appears in a process argument list. Avoid `curl -H "Authorization: Bearer $TOKEN"`.

Missing, malformed, duplicated, or wrong bearer headers receive `401` with `WWW-Authenticate: Bearer`, including on unknown `/v1` paths. Tokens in query strings are ignored. After 30 failed attempts in a minute, further failures receive `429` with `Retry-After`; the valid token still works. Requests carrying an `Origin` header receive `403`, and a `Host` that is not a loopback name receives `400`. The Host port is not checked, so a tunnel's local port works. Provider processes will never inherit either credential.

To rotate the owner token, stop the API, move the old file away, run `setup`, update the desktop's copy, and restart. Rotation does not touch `SECRET_KEY`.

`GET /healthz` returns `{"status":"ok"}` while the process serves HTTP. It requires no authentication and reports liveness only. All errors use the JSON shape from the [desktop contract](research/desktop-and-feature-contracts.md#proposed-rest-endpoints).

### PostgreSQL tests

`cargo test --workspace` includes tests that need the Compose PostgreSQL service. Each test creates its own `else_test_<uuid>` database, applies migrations, and drops it with `WITH (FORCE)` when the test ends. The application database is never used. Set `TEST_DATABASE_URL` to use a different server; its user needs `CREATEDB`. Start the service with `docker compose up -d --wait` before running tests. The whole-assistant acceptance run (`ELSE_LIVE_ACCEPTANCE=1`, `--test acceptance_live`) and the VM automation and categories milestone run (`ELSE_LIVE_MILESTONE=1`, `--test milestone_live`) are described in [acceptance.md](implementation/acceptance.md). The replication tests (`--test replication`) likewise require the Compose S3 emulator and fail with a message naming it when it is not reachable; each uses its own bucket, and some stop or restart the `seaweedfs` container.

## Run the desktop

The desktop is a native GPUI window built with [GPUI Kit](https://gpui-kit.com) `gpui-kit = "=0.8.1"`, which pins GPUI as `gpui-pre 0.3.10`. The pin is exact because GPUI is pre-1.0. It was built and run on Arch Linux (Omarchy) with Hyprland 0.56.2 on Wayland and Rust 1.98.0. Linux needs `libxkbcommon`, `libxcb`, `fontconfig`, and `freetype2`, plus a Vulkan-capable graphics driver; Wayland and X11 sessions are both supported by GPUI. The first build compiles GPUI and takes a few minutes.

Start the API, then the desktop. The desktop reads the same root `.env` as the API, so `ELSE_DATA_DIR` or `OWNER_TOKEN_FILE` set there apply to both:

```sh
cargo run -p else-desktop
```

| Variable | Default | Purpose |
| --- | --- | --- |
| `ELSE_API_URL` | `http://127.0.0.1:7879` | API origin (the development API; `elsebot desktop` uses the installation's 7878). Only `http://` loopback origins without a path, query, or credentials are accepted; this build has no TLS. For a remote server use `ssh -L 7878:127.0.0.1:7878 <server>`. |
| `ELSE_OWNER_TOKEN_FILE` (or the API's `OWNER_TOKEN_FILE`) | `$ELSE_DATA_DIR/owner-token`, else `$XDG_DATA_HOME/else-bot/owner-token`, else `~/.local/share/else-bot/owner-token` | The owner token written by `else-api setup`. It must be a regular file you own with mode `0600`; symbolic links are refused. |
| `ELSE_OWNER_TOKEN` | unset | Token value for a development launcher. Takes precedence over the file. Prefer the file. |

The window lists bots on the left and the selected conversation on the right. New bot opens a dialog for the name and role; deleting asks for confirmation, keeps history, and shows the bot as Deleting until its work has stopped. The header shows Stop work while the bot is busy, the category, and Delete; each message goes to the bot's own provider and model. With categories (POC-031), the sidebar groups bots under a header per category, in the server's order (case-folded name, then ID), each listing its bots by name with a count, Rename and Delete; empty categories stay visible with No bots, and bots without a category, or whose category the desktop does not know, sit under Unassigned. Without categories the list is flat, by name. New category (and Rename) opens a dialog; a create whose outcome is unknown is retried unchanged under the same request ID, and a dismissed dialog never receives a late result. The list itself changes only from the server's `bots` snapshots, the one ordered source: category operations neither patch it locally nor fetch it again, so a slower response cannot undo a newer change. A failed category operation is shown in the sidebar, under the connection status. Deleting a category says that its bots are kept and move to Unassigned and that no bot, conversation, memory, or file is deleted. The create-bot dialog offers the categories as a radio group (Tab to one, Space to choose, Enter creates), and the header's Category button opens a Move dialog with a radio group of every category and Unassigned (Tab, Space, then Enter or Move; Esc closes). One move per bot is in flight at a time: the button shows Moving… until the server answers, so an earlier choice can never land after a later one. Moving or renaming never changes the selection, the draft, the Main marker, the activity, or running work; Up/Down follow the grouped order. Replies stream into the transcript as the API commits them; per-turn notes show Queued, Working, Stopped, Failed, or Outcome unknown. Drafts are kept per bot while the desktop runs. A message whose send outcome is unknown stays visible as Not confirmed with Retry; after reconnecting the desktop asks the API whether it arrived and resends it under the same request ID only if it did not. The view follows new output only while it is at the bottom.

| Keys | Action |
| --- | --- |
| Up/Down, Ctrl+N/Ctrl+P | Select the next or previous bot while the sidebar has focus |
| Enter (sidebar) / Escape (composer) | Move focus to the composer / back to the sidebar |
| Enter / Shift+Enter | Send / insert a new line |
| Ctrl+Shift+N | New bot |
| Ctrl+Shift+X | Stop work |
| Ctrl+Shift+D | Delete the selected bot |
| Ctrl+Shift+Up | Load older messages |
| Ctrl+Shift+G | New category |
| Ctrl+Shift+M | Move the selected bot to another category |

The token is sent only as an `Authorization` header to the configured origin. Redirects are never followed, and the token never appears in URLs, logs, or messages. A missing or invalid configuration, a rejected token, or an unreachable API is shown in the sidebar; loaded bots stay visible while the desktop retries. The sidebar and the open conversation update live over the WebSocket; nothing polls. Up/Down (or Ctrl+N/Ctrl+P) move the selection while the sidebar has focus. Closing the window quits the desktop; work already accepted by the API keeps running.

`scripts/demo.sh` runs a disposable installation for manual checks, with its own `else_demo` database and `/tmp/else-demo` data directory and the synthetic provider enabled: `scripts/demo.sh reset`, then `scripts/demo.sh api` and `scripts/demo.sh desktop` in separate terminals. `scripts/demo.sh drop` removes it.

The workspace shares its root `Cargo.lock` and `target` directory. The backup research crate remains excluded so its documented standalone commands still work. See [Cargo workspaces](https://doc.rust-lang.org/cargo/reference/workspaces.html).

## Stop and resume services

Stop containers and remove their network while preserving the database volume:

```sh
docker compose down
```

Run `docker compose up -d --wait` to recreate the container with the saved database. Initialization settings apply only to an empty volume. Changing the database name, user, or password in `.env` does not rewrite an existing database. Apply deliberate SQL changes when updating an initialized installation. The [official image documentation](https://hub.docker.com/_/postgres) describes this initialization behavior.

For a disposable development database that you explicitly want to erase, remove its volume:

```sh
docker compose down --volumes
```

This deletes the current Compose project's database. Use ordinary `down` when you want to retain it.
