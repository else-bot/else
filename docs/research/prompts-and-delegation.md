# Prompts and delegation research

Research date: 2026-11-02. Track: prompts. This report preserves the accepted host CLI, subscription authentication, native sessions, PostgreSQL, Rust API, GPUI, and per-bot Microsandbox design. The first UI remains bot messaging and bot creation and deletion. Family and work are example roles, not separate product modules.

The small design is a main bot that can call registered leaf bots, plus ordinary direct conversations with any bot. Prompts decide whether delegation helps. The Rust API checks whether the requested operation is allowed. A bot registry and a bounded task record are enough. No agent framework or independent agent inside each guest is needed.

`VERIFIED` means observed in the recorded local experiment. `DESIGNED` means a proposed else.bot rule. `UNVERIFIED` identifies a gap. A passing model response does not establish a security boundary.

## Prompt package

DESIGNED: persist a versioned prompt package in PostgreSQL. Compile these inputs into trusted instructions:

| Input | Minimal content |
| --- | --- |
| Shared behavior | Report actual outcomes, preserve scope, distinguish source evidence from instructions, use guest tools for computer work. |
| Current bot | Immutable ID, display name, owner-approved role, available tools. A role never grants access. |
| Owner settings | Approved preferences and time zone. Only authenticated settings changes update standing instructions. |
| Current task context | Server-derived bot, root task, ancestry, delegation budget, operation limits, and permitted memory targets. |
| Active registry snapshot | Stable bot IDs and short roles. Include only bots available to this installation. |

Keep current user text, retrieved memory, guest output, historical messages, handoffs, and delegated results outside the trusted instruction package. Label each source and retain its source ID. An external email quoted in memory stays external email after retrieval or summarization. A bot result is derived task data even when it says "owner approved". Source labels establish provenance, not truth. These rules preserve the existing [prompt drafts](../prompts.md), [provider design](../providers.md), [memory requirements](../memory.md), and [security requirements](../security.md).

The [tested v1 prompt](../experiments/prompts/prompt.txt) contains the routing, leaf-task, trust, approval, and guest-boundary language used in the original 13 cases. The [v2 async prompt](../experiments/prompts/prompt-async.txt) adds the scheduling rule below. Its evidence is recorded separately in the async cases, not retroactively attributed to v1. Both prompts restrict the experiment to synthetic tools. Production supplies the actual scoped tool inventory instead. Record the prompt version, registry revision, provider version, model settings, and tool outcomes with each turn. Do not insert credentials into the package.

## One-hop delegation

DESIGNED: start with one delegation level. The main bot may delegate at most two subtasks per owner turn. A leaf gets zero remaining delegations, even if the task text asks it to send work back to main. A direct message to a leaf bot stays with that bot. The owner can explicitly ask main to coordinate a later turn.

| Operation | Model supplies | API determines and checks |
| --- | --- | --- |
| `delegate` | Target bot ID and bounded task description | Caller, root request, active target, current budget, inherited restrictions, task identity, and duplicate request status. |
| `memory_search` | Target bot ID and query | Caller identity and whether this task may read that bot's memory. |
| Guest operation | Guest command or guest artifact reference | Assigned VM, allowed operation, guest path handling, lease, limits, and job status. |
| Approval-gated operation | Action and target | Whether a stored owner approval covers the exact action, target, parameters, and task. |

The last row is a future policy boundary tested with a synthetic operation. It adds no approval UI or connector to the messaging MVP. The experiment's explicit preapproval of harmless MCP transport calls is separate from action authorization in the API.

DESIGNED: the Rust API accepts a delegation under the same task restrictions, records the parent and target, and consumes the root's remaining budget. Granting a child its bot's broader permissions would break scope inheritance. Use the normal bot-conversation execution queue. A short internal task conversation keeps delegated work separate from the owner's direct conversation with that bot. Reuse the bot's scoped tools and memory access. No second queue system is needed.

Delegation is async-first because a valid deployment has only one host-provider slot. Waiting for a child inside the parent's CLI process would occupy that slot and deadlock. The initial design always uses this sequence:

1. `delegate` records the accepted child and returns `pending` with a stable task ID immediately. It never waits for child inference.
2. The parent records that pending ID and ends its provider attempt. Its prompt forbids polling, sleeping, waiting, and further tool calls after the pending response. The scheduler does not infer child readiness from conversational text. The Rust adapter completes or interrupts and reaps the parent process before releasing its slot.
3. The owner task remains `working`, with a recorded reason that it awaits this child. The ended provider attempt is a separate record. Freeing a slot does not mark the owner task complete.
4. The ordinary scheduler runs the queued child in the freed slot. The leaf cannot delegate. It records its result or terminal failure before scheduling the parent continuation.
5. The scheduler resumes the parent's native session or creates a fresh attempt with its saved prompt, original owner request, pending child reference, and recorded result. The parent answers or continues from that outcome. It does not resubmit completed work.

Use a child task ID and queued, running, completed, failed, and cancelled states. Represent the parent's wait with the awaited child ID and no active attempt. Give retries the same server-derived request identity so reconnects do not create another child. The API supplies task context from saved records, never from model claims in task text. It also rejects follow-on operations from an attempt parked after delegation. A short grace period followed by interruption prevents a model that ignores the prompt from occupying the slot indefinitely. Enforce that rule in the adapter, independently of model cooperation.

Each main attempt can submit one child before parking. After continuation, it may submit a second child if the root still has budget. At most two children and one hop need ordinary task and attempt records, not a workflow engine. Do not add a synchronous optimization initially. Any future synchronous path requires a guaranteed spare slot and immediate async fallback when capacity is unavailable. The v1 fixture's immediate completed response is only a tool-behavior test; it is not the integration design.

Recheck target existence at acceptance. If a bot disappears after the registry snapshot, return `BOT_UNAVAILABLE`; the main bot explains the failure. Do not create a replacement or choose another bot silently. If deletion follows acceptance, cancel pending child work and reject further calls from its revoked tool session. Preserve recorded outcomes for the originating conversation. Bot deletion and guest teardown belong to the existing API lifecycle, not prompt text.

## Actual synthetic inference

VERIFIED: the experiment runs the installed CLI against a disposable Python stdio MCP server. The model makes real MCP calls. The server records actual arguments and returns synthetic data. Its `delegate` response is scripted; it does not run another model. Family-leaf and loop cases use separate actual model invocations. `guest_run` returns a constant fixture result and never executes the model's command. This establishes tool selection and response handling, not real delegation delivery or VM isolation.

The runner uses an explicit `/tmp/elsebot-research-prompts` working directory, read-only command sandbox, `approval_policy=never`, ephemeral sessions, no user config or rules, and no project instructions. It disables native shell, apps, plugins, hooks, browser, computer use, image generation, and native multi-agent features. The scoped fixture is the only configured MCP server. Zero native command events is an observed property of these runs, not proof that every possible host escape is unavailable.

Initial failures were useful. The restricted outer environment failed CLI initialization with `Read-only file system`. An authorized host invocation then succeeded. Two tool pilots reached Codex's MCP gate but failed with `MCP tool call requires approval, but approval policy is never`. Setting MCP mode `auto` alone did not fix that. Those outputs remain in [initial results](../experiments/prompts/results) and [the auto-mode trial](../experiments/prompts/results-auto).

The final fixture advertises accurate synthetic read-only, non-destructive, closed-world annotations and uses `mcp_servers.elsebot.default_tools_approval_mode="approve"`. A [pilot after that change](../experiments/prompts/results-approved/family-delegate) reached the server. Because both annotations and approval mode changed, this experiment does not isolate which change enabled dispatch. Real guest and delegation tools change state and must not copy these annotations. Configure approval behavior only for API-guarded tools whose operation is already authorized. These configuration controls are documented by OpenAI. [MCP configuration](https://learn.chatgpt.com/docs/extend/mcp?surface=cli).

The prompt text itself did not need an iteration during these trials. The observed iteration corrected transport configuration. Full per-case developer prompts, owner inputs, invocation arguments, CLI events, tool requests and responses, final answers, and checks are preserved under [final results](../experiments/prompts/results-final).

## Reproduction and limits

Run the local scripted checks without inference:

```sh
python docs/experiments/prompts/check_fixture.py
```

VERIFIED: all 17 checks pass in [fixture-checks.json](../experiments/prompts/fixture-checks.json). They exercise the Python guard model for nonexistent and deleted bots, cycles, leaf restrictions, budget exhaustion, scope denial, forged identity or approval arguments, and guest access denial. This is not Rust API validation. The fixture's host-path string check is intentionally synthetic and is not a usable isolation control.

The following commands use the existing subscription through Codex and require network and host runtime access. Use a fresh output directory for each run to preserve prior evidence.

```sh
python docs/experiments/prompts/probe.py
python docs/experiments/prompts/probe.py --infer
python docs/experiments/prompts/run.py --infer --output /tmp/elsebot-research-prompts/replay
python docs/experiments/prompts/run.py --infer --cases docs/experiments/prompts/cases-async.json --prompt docs/experiments/prompts/prompt-async.txt --output /tmp/elsebot-research-prompts/replay-async
```

Each inference case has a 55-second timeout, then at most three seconds before forced process-group termination. The batch stops starting cases after 720 seconds, so its maximum wall time can exceed 720 by one case's cleanup window. The filtered-output recorder has a three-second join limit. The fixture rejects calls after six calls per case. Each MCP startup and tool timeout is ten seconds. The tier probe has a 40-second turn wait, 30-second waits for protocol responses, and a three-second shutdown timeout. Its recorded invocation also used an outer 60-second limit. There is no explicit provider output-token limit in the CLI cases. The stop conditions bound elapsed time and tool dispatch, not exact subscription usage.

The async runner drops reasoning events before writing CLI event logs. The existing v1 logs were checked and contained zero raw reasoning events. The tier probe records only selected lifecycle and completed message events. Retained reasoning effort and token counts are configuration and usage metadata. No environment dump or authentication material is saved. Future cases must continue to use synthetic source text and fixture responses.

UNVERIFIED: actual Rust API authorization, revoked sessions after deletion, transaction-level budget and retry handling, asynchronous child delivery, real guest leases and isolation, host filesystem restrictions, native session resume, compaction, provider-switch handoffs, and Claude behavior. No email, note, kanban, routine, or mobile feature was implemented. Injection coverage is a small single-sample suite, not a guarantee against future attacks. Before shipping, run the same cases against the real scoped API and both provider adapters, with disposable canaries and actual denied access checks.
